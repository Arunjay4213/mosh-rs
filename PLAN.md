# mosh-rs: a Rust reimplementation of mosh

Version 2 of the plan, 2026-10-13.
Working name `mosh-rs` (rename before publishing).
License GPLv3, because the code is ported from upstream mosh (GPLv3, Keith Winstein et al.).
Port source: upstream git master at commit decd9b7 (2026-03-22, 39 commits after the `mosh-1.4.0` tag), which is what `~/src/mosh` on devbox contains. Interop and `make check` compatibility are proven against the mosh 1.4.0 release binaries from apt.
Goal: one static Rust binary per platform that talks to every existing mosh-server, runs natively on Windows, and adds scrollback.

All work happens on devbox (`~/mosh-rs`), inside a Claude Code session running in tmux.
Upstream source and a built upstream tree live at `~/src/mosh`, symlinked as `~/mosh-rs/upstream`.
Real mosh 1.4.0 from apt is installed on devbox as `mosh`, `mosh-client`, `mosh-server`.

## 0. Decisions

- Port upstream file by file, preserving control flow and every constant. Do not "improve" semantics. Every deliberate deviation is listed in section 9 and nowhere else.
- Correctness is proven by differential testing against upstream's own C++ code, by interop with real mosh in both directions, and by end-to-end tests. Not by unit tests.
- Protocol version stays 2. New features are additive protobuf fields that old peers ignore.
- No async runtime. One poll loop with a computed timeout, exactly like upstream's select loop.
- Four crates. No trait unless there are at least two real implementations.

## 1. What mosh is (what we are rebuilding)

A mosh session has four layers, bottom to top.

1. Crypto (`upstream/src/crypto`).
   Every UDP packet is AES-128 in OCB3 mode (RFC 7253) with a 16-byte tag.
   The 128-bit key is generated by the server, printed once over ssh as 22 base64 characters, and never sent again.
   The nonce is 12 bytes: 4 zero bytes then a big-endian u64 whose top bit is the direction (1 = to client) and whose low 63 bits are the packet sequence number.
   The wire packet is the 8 nonce bytes followed by the OCB ciphertext.
   Inside the plaintext: a 16-bit timestamp, a 16-bit timestamp echo (for round-trip timing), then the payload.
2. Transport, called SSP (`upstream/src/network`).
   Neither side streams bytes.
   Each side keeps numbered snapshots of a state object and sends a `TransportBuffers::Instruction`: old_num, new_num, ack_num, throwaway_num, and `diff`, the bytes that turn state old_num into state new_num.
   Diffs are zlib-compressed and split into fragments (id, fragment number, final flag) that fit in one UDP packet.
   The sender picks send intervals from measured round-trip time, retransmits when unacked, and the server adopts a new client address whenever a valid packet arrives from one.
   That last rule is roaming.
3. State objects (`upstream/src/statesync`).
   Client-to-server state is `UserStream`: an ordered list of keystroke and resize events (`userinput.proto`).
   Server-to-client state is `CompleteTerminal`: a full terminal framebuffer plus an echo-ack counter (`hostinput.proto`).
   The server-to-client diff is not raw program output.
   It is an ANSI escape string computed by `Display::new_frame` that redraws the client's mirror framebuffer from the old snapshot to the new one.
   The client feeds that string into its own copy of the emulator.
   So both ends run the same emulator, and the client's emulator must interpret that redraw subset exactly as upstream's does, or the mirror drifts and never recovers.
4. Frontend (`upstream/src/frontend`, `upstream/scripts/mosh.pl`).
   `mosh-server` parses `SSH_CONNECTION`, binds a UDP port in 60000-61000, prints `MOSH CONNECT <port> <key>`, forks, detaches from the ssh session, and runs the user's shell under a pseudoterminal.
   `mosh-client` puts the local terminal in raw mode, runs the poll loop, renders the mirror framebuffer to the real terminal, shows the status line, and runs the prediction overlay (local echo of typed characters, later confirmed or corrected by the server).
   `mosh` (Perl upstream) runs `ssh host -- mosh-server new ...`, reads the `MOSH CONNECT` line, and starts the client with the key in `MOSH_KEY`.

Upstream size: 16,964 lines of C++ and protobuf.
The terminal emulator (4,704 lines) and the prediction overlay (1,240 lines) are the hard parts.

## 2. Architecture

One Cargo workspace, four crates, plus tooling that is not shipped.

- `crates/terminal`: parser state machine, framebuffer, dispatcher, terminal functions, `Display` (render and `new_frame`).
  Pure Rust, no I/O, no platform code.
  Ported from `upstream/src/terminal`.
  Type and method names mirror upstream (`Complete`, `Framebuffer`, `DrawState`, `Cell`, `Row`, `Display`) so the frontend port can follow upstream line by line.
- `crates/network`: `crypto` (OCB3 session, key, nonce), `proto` (hand-written `prost` structs, no `.proto` compilation, no build script), `transport` (fragments, compression, sender, receiver, connection, timing, roaming).
  Transport is generic over a `State` trait with exactly the methods upstream's template requires: `diff_from`, `init_diff`, `apply_string`, `subtract`, `reset_input`, `compare` (the sender's verbose round-trip check, which upstream's `make check` greps for), and equality, plus `subtract_self` for upstream's `subtract( this )` call on the front state, which Rust borrows cannot express as aliasing (default: subtract a copy; `UserStream` overrides with clear, `Complete` with nothing).
  Sockets via `mosh-platform` (`mosh_platform::socket`); the crate itself has no `unsafe` and no `#[cfg]` platform code (`#![forbid(unsafe_code)]`).
  Ported from `upstream/src/crypto` and `upstream/src/network`.
- `crates/platform`: the only crate with `#[cfg(unix)]` and `#[cfg(windows)]` code.
  Local terminal: raw mode on and off, size query, resize detection, blocking byte reads on a thread, byte writes.
  Pseudoterminal: forkpty, window size, child wait (unix only).
  Process: spawn `ssh` and read its output (both platforms).
  UDP sockets for `crates/network` (`socket`: creation with upstream's options, numeric `getaddrinfo`, bind, `recvmsg` with the ECN mark) and core-dump control (`coredump`, unix only).
- `crates/mosh`: `statesync` (`UserStream`, `Complete`), the client (`stmclient`, `terminaloverlay`), the server, and the launcher.
  Produces three executables with upstream's names and flags: `mosh`, `mosh-client`, `mosh-server`.
  Upstream's test harness and existing user scripts work unchanged.
- `ref/`: tiny C++ programs linked against the upstream build, used as oracles. Not shipped.
- `tools/`: `udp-impair` (a UDP proxy with loss, delay, reordering, and client-address change), corpus recorder, perf bench. Not shipped.
- `tests/`: the end-to-end and conformance tests described in section 3, run with `cargo test --release` plus shell drivers.

Dependencies: `aes`, `ocb3`, `rand`, `prost`, `flate2` (with the `zlib-rs` backend), `nix`, `libc`, `windows-sys`, `unicode-width`, `lexopt`.
Nothing else without a reason written in the PR.

## 3. Correctness strategy (the oracles)

Each oracle is a program we can run, not an opinion.

1. Reference harnesses in `ref/`, built against upstream object files on devbox.
   - `ref-term`: reads bytes on stdin, feeds them to upstream `Terminal::Complete` at a given size, dumps the framebuffer in a fixed text format (every cell: text, width, attributes, fg, bg; cursor; cursor visibility; title; mode flags).
   - `ref-term --frame OLD NEW`: feeds two byte streams, dumps upstream `Display(false).new_frame(true, old, new)` as bytes.
   - `ref-crypto`: key, direction, sequence number, and payload in; wire packet out, and the reverse.
   Our Rust binaries `vt-check` and `crypto-check` print the identical formats.
   Conformance means `diff` is empty.
2. Differential fuzzing of the emulator.
   A generator biased toward escape sequences (CSI with random params, SGR, OSC, DEC private modes, UTF-8 including wide and combining characters, invalid bytes) produces millions of inputs.
   Each is run through `ref-term` and `vt-check`; the first mismatch is minimized and fixed.
   `new_frame` must be byte-exact against the reference on every pair of corpus states.
3. Corpus of real sessions, recorded on devbox with a pty recorder: bash with colors, vim editing a file, less on a man page, htop, tmux inside the session, the Claude Code TUI, `seq 1 100000`, a 256-color and truecolor test, a wide-character and emoji test.
   Every corpus file is a conformance input for oracle 1.
4. Interop matrix over loopback through `udp-impair`.
   {Rust client, C++ client} × {Rust server, C++ server} × {clean, 5% loss, 30% loss with 200 ms delay and reordering, 2-minute blackout, client address change mid-session}.
   Each cell runs a scripted session inside tmux and compares the final `tmux capture-pane` to a direct (no mosh) run of the same script.
   Also asserts: the session is still live after the blackout, and the server adopted the new address after the change.
5. Upstream's own test suite.
   Copy our `mosh-client` and `mosh-server` over the binaries in `upstream/src/frontend/` and run `make check` in `upstream/`.
   Every upstream e2e test must pass with our binaries.
6. Scrollback oracle.
   tmux is the host terminal with `history-limit 200000`.
   Run `seq 1 50000` over mosh-rs, then `tmux capture-pane -S -200000` and compare scrollback plus screen to `seq 1 50000` exactly: no gaps, no duplicates, no blank lines.
   Repeat with 30% loss, with a vim excursion in the middle (vim output must not appear in scrollback), and with a resize in the middle.
7. Performance bench, compared with C++ mosh in the same harness (section 5).
8. Human end-to-end.
   `mosh devbox` from WSL and from Windows Terminal over Tailscale, sleep the laptop, wake it, the session is live and scrollback works.

## 4. Testing rules

- No unit tests of individual functions. No mocks. No test-only traits or abstractions in shipped code.
- Every test exercises a feature a user would notice: screen correctness, survival under loss and roaming, scrollback integrity, prediction behavior under latency, exit codes, resource usage.
- Tests live in `tests/` as cargo integration tests or shell drivers, and run with one command: `tests/run-all.sh`.
- A test that cannot fail for a real reason is deleted.
- The agent that writes a module also makes it pass the relevant oracle before reporting. The report contains the commands and their real output.

## 5. Performance targets

Measured by `tools/bench` against C++ mosh 1.4.0 on devbox, and published in the README as measured numbers.

- Idle CPU of client and server over 60 seconds: 0.0% (no polling faster than the computed send interval).
- Resident memory, client and server, after a 1-hour session: no more than C++ mosh.
- Static binary size: under 4 MB.
- Startup: the client's own startup (exec to its first terminal write) under 20 ms, and the first frame on loopback no slower than C++ mosh. (The original target, first frame under 20 ms, cannot be met with upstream's timing: the round-trip estimate starts at 1000 ms (`network.cc` `SRTT( 1000 )`), so the first send interval is the 250 ms maximum, and both implementations show the first frame after about 252-257 ms.)
- Keystroke to screen with prediction: one render, no visible delay at 300 ms simulated RTT.
- `seq 1 100000` through mosh on loopback: no slower than C++ mosh.
- Release profile: `opt-level = 3`, `lto = "fat"`, `codegen-units = 1`, `panic = "unwind"` (the client restores the terminal from a panic hook).
- Linux releases are static musl binaries.

## 6. Scrollback design

Why upstream has none: the client enters the alternate screen (`Display::open` sends smcup), so the host terminal never scrolls and never accumulates history.
The server's framebuffer also discards rows that scroll off, so lines that pass between two frames are gone.
Upstream's `new_frame` already detects full-screen scrolls and emits newlines at the bottom row (`terminaldisplay.cc` lines 168-243), which is why a client patched to skip smcup gets partial scrollback with gaps and with the status line leaking into history.

Design, all gated on negotiation so old peers see byte-identical behavior:

1. Negotiation.
   New `ClientBuffers::Instruction` field 4, `ClientCapabilities { optional bool scrollback = 1; }`.
   The client puts it as the first event in its `UserStream`.
   Upstream `UserStream::apply_string` ignores unknown extensions (`user.cc` if/else-if chain), so an old server sees nothing.
   A new server that applies it turns scrollback mode on for that session.
   Encoded alone it is the `UserMessage` bytes `0a 04 22 02 08 01`; upstream's `UserStream::apply_string` was fed those bytes plus a keystroke and a resize and returned only the keystroke and the resize.
   Like any non-empty user diff, a diff holding only the capability registers an input frame on the server (one echo ack).
2. Server capture.
   The `Framebuffer::scroll` path records each row that leaves the top when the scroll region is the full screen and the remote program has not enabled the alternate screen (DEC mode 1049, 1047 or 47, tracked as a new flag in `DrawState`; upstream ignores those modes entirely).
   Rows are rendered to ANSI strings with the same row renderer `new_frame` uses, and appended to a ring buffer (default 10,000 lines, server flag `--scrollback N`).
   The ring lives outside the state object, shared by `Rc`, so copying `Complete` for the sender's state history stays cheap.
   `Complete` carries only `scrolled_total: u64`.
   Capture interface (settled by the server agent): the terminal crate knows nothing of mosh.
   `Framebuffer::set_scroll_capture(true)` makes `scroll` append the leaving rows (shared `Rc<Row>`, no copy) to a list that `Framebuffer::take_scrolled_rows` empties; `Complete::act` empties it after every call, renders each row and pushes it into the ring, so the list is always empty when a state is copied.
   Diffs applied with `apply_string` discard captured rows (a copy of a server state applying a diff, as the sender's round-trip check does, must not add history).
   Rows created or last written while the alternate-screen flag is on carry a mark (`Row::alternate`, not part of row equality) and are never captured, also after the program left the alternate screen: upstream keeps that screen's rows on display, so vim's last screen would otherwise scroll into history when the shell continues.
   Line format (`Display::render_scrolled_row`): `put_row` on an uninitialized one-row frame, assuming neither ECH nor back-color erase.
   The line is written at row 1 column 1 with default renditions and no hyperlink, ends with default renditions and no hyperlink, holds no line feed and no cursor visibility change, and its only cursor movement is `CSI 1 ; <col> H` before the last cell of a row that wrapped.
   Blank runs are spaces except default-colored blanks at the end of the row, which are `CSI K`.
   A wrapped row does not carry its soft-wrap flag.
3. Wire.
   New `HostBuffers::Instruction` field 9, `ScrolledLines { optional uint64 first_index = 1; repeated bytes line = 2; optional uint64 dropped = 3; }`.
   `Complete::diff_from(existing)` includes the lines with index in `(existing.scrolled_total, self.scrolled_total]` that are still in the ring, and `dropped` for any that were evicted.
   `Complete` equality includes `scrolled_total` when scrollback mode is on (otherwise `yes | head` would scroll without the framebuffer changing and nothing would be sent).
   Settled by the server agent: lines are numbered from 1 in the order they left the screen.
   `first_index` is the number of `line[0]` (one past the last number covered when no line is left), and `dropped` (absent when 0) counts the evicted lines just before it, so a diff from `existing` covers exactly `(existing.scrolled_total, first_index - 1 + line count]`.
   Instruction order in a `HostMessage`: echo ack, scrolled lines, resize, host bytes.
   A client prints the lines first, then applies the frame.
   Client side: `Complete::enable_scrollback_receive` returns a queue shared by every copy of the client's state; `apply_string` adds each line with its number, skips numbers it already has (a diff from an older state, sent again after loss, repeats lines) and counts a jump forward as lost.
   Open (server agent's report, 2026-10-13): nothing bounds the size of one diff, and `seq 1 50000` puts the whole burst in one diff.
   Then the oldest lines are evicted before they are sent (default ring), or the diff is about 87 fragments, sent as one burst, of which the client's UDP receive buffer drops some, and every resend has a new instruction id, so it seldom completes; under 30% loss even 10,000 lines (about 17 fragments) never arrived in 120 s.
4. Client rendering.
   In scrollback mode the client does not send smcup, and runs `new_frame` with scroll detection off.
   Before each render, for each pending scrolled line L: cursor to row 1 column 1, write L, cursor to the last row, write `\n`.
   The host terminal moves row 1 (which is now L) into its history and shifts the screen up one row.
   After injecting S lines, the client's last-frame copy is shifted up by S rows with S blank rows appended, then `new_frame` runs as usual.
   For a one-line scroll this degenerates to one newline plus one row repaint, same cost as today.
   The whole render is wrapped in synchronized output (`\e[?2026h` ... `\e[?2026l`), which terminals that lack it ignore.
5. Compatibility.
   Old client, new server: no capability arrives, scrollback mode stays off, behavior identical to upstream.
   New client, old server: no `ScrolledLines` ever arrive, the screen is repainted in place, no history accumulates, and the client prints a one-line notice that the server does not support scrollback.
6. Stretch, only after oracle 6 passes.
   Forward the alternate-screen flag to the host terminal (emit 1049h/l on transitions, then a full repaint), so the mouse wheel inside vim behaves as it does over ssh and the pre-vim screen is restored on exit.

## 7. Windows client

- Console setup: `SetConsoleMode` with `ENABLE_VIRTUAL_TERMINAL_PROCESSING` on stdout and `ENABLE_VIRTUAL_TERMINAL_INPUT` on stdin, processed input off, `SetConsoleCP`/`SetConsoleOutputCP` to UTF-8.
  After that, keys arrive as the same escape-sequence bytes a unix tty produces, and output is plain VT bytes.
  No key-event decoding and re-encoding layer.
- Resize: poll `GetConsoleScreenBufferInfo` on every loop iteration (the loop already wakes at least every 50 ms).
- Ctrl+C arrives as byte 0x03 and goes to the server like any key.
- ssh: spawn `ssh.exe` from the Windows OpenSSH that ships with Windows 10 and later.
- Build: cross-compile on devbox for `x86_64-pc-windows-gnu` with the mingw package already available there, copy the exe to the laptop for testing. Releases use the MSVC target built on a Windows GitHub Actions runner.
- `mosh-server` is unix only, as upstream.
- TERM: Windows normally has none. If TERM is unset or empty when `mosh.exe` or `mosh-client.exe` starts, it sets `TERM=xterm-256color` for itself and its children (`mosh_platform::tty::default_term_if_unset`, section 9 item 12), which Windows Terminal and conhost with VT processing implement. On unix nothing changes.

## 8. Launcher

The launcher ports mosh.pl, including its address discovery: it runs ssh with `-S none -o ProxyCommand='<own exe>' '--family=<family>' --fake-proxy -- %h %p`.
In that mode the launcher resolves `%h` (the hostname after `~/.ssh/config`) with the system resolver (MagicDNS names like `devbox` resolve to the Tailscale address), orders or filters the addresses by `--family`, opens a TCP connection to the first one that accepts it on `%p`, prints `MOSH IP <address>` on stderr and relays the ssh session over that connection.
So mosh-server sees that address in `SSH_CONNECTION` and binds it, and the client is started with the same address; on hosts with both IPv4 and IPv6 addresses the two cannot disagree.
Host key checking is untouched because ssh still connects to the name the user typed.
An earlier design (`ssh -G`, then resolving the name separately) was dropped: on dual-stack hosts ssh and the client could pick different address families (INTERVENTIONS.md, 2026-10-13), and `-o HostName=<ip> -o HostKeyAlias=...` cannot reproduce ssh's known_hosts lookup for non-default ports (`[host]:port` with fallback to `host`).
Supported flags for v0.1: `--server`, `--ssh`, `--port`, `--predict`, `--no-init`, `--local`, `-4`/`-6`, `--scrollback`, and the `user@host` and trailing command forms.

## 9. Deviations from upstream (the only allowed ones)

1. Withdrawn (was: launcher uses `ssh -G` instead of `--fake-proxy`). The launcher ports `--fake-proxy` as mosh.pl does (section 8). The number is kept so references to items 2-10 stay valid.
2. utmp/wtmp records are not written.
3. `--bind-server` supports `ssh` and `any` only.
4. Scrollback extension (section 6), alternate-screen flag in `DrawState`.
5. Synchronized output around client renders.
6. Runtime terminfo lookup is replaced by a table generated at build-authoring time from every entry in the devbox terminfo database (ncurses 6.4, plus the kitty-terminfo package), holding exactly the capabilities upstream reads (ech, bce, smcup, rmcup, and what it uses for title support). An exact TERM match gives the same answer upstream would get; an unknown TERM falls back to xterm where upstream would fail to start. The table also carries `colors`, so `mosh-client -c` answers from it; for an unknown TERM it prints xterm's count where upstream prints "unknown terminal type" and exits 1. Needed because Windows has no terminfo.
7. Timestamps start at 1,000,000,000 ms instead of milliseconds since boot, so upstream's `now - 0` comparisons behave as they do on a machine that has been up for a while.
8. Malformed input from a peer that holds the session key returns an error and drops the packet where upstream aborts the process with `fatal_assert` or `assert` (short fragment, conflicting duplicate fragment, fragment index past the final one, undecodable protobuf, `throwaway_num` above every received state, oversized ciphertext handed to `Session::decrypt`, and a state diff that `State::apply_string` cannot apply: a `UserMessage` or `HostMessage` that does not decode, a resize below 1x1 in either, host bytes that make the client emulator reply, or an echo ack lower than the current one). `State::apply_string` returns `Result` for this.
9. Two places where upstream dereferences an erased iterator (undefined behavior) are made defined: `add_sent_state` moves `assumed_receiver_state` to the previous element when the assumed one is erased, and `Transport::recv` looks the reference state up again after `process_throwaway_until` and drops the instruction if it is gone.
10. Withdrawn (was: the `State` trait omits upstream's `compare`). `compare` is back in the trait and the sender runs upstream's verbose round-trip check, so upstream's `make check` catches a wrong server diff in our binaries too. The number is kept so references to item 11 stay valid.
11. Where upstream's client crashes or aborts with the terminal left raw, the client exits cleanly: if the window size cannot be read at startup it prints the error and exits 1 (upstream returns early from `STMClient::init` and then dereferences a missing network object, `stmclient.cc` lines 247-250), and a panic restores the terminal through the panic hook (section 5).
12. On Windows only, `mosh` and `mosh-client` set `TERM=xterm-256color` for themselves when TERM is unset or empty at startup (section 7). Upstream's client prints "TERM environment variable not set." and exits 1 there, so the launcher stops with "Can't count colors" and a stock Windows Terminal could never connect. Unix keeps upstream's behavior.

Anything else that differs from upstream is a bug.

## 10. Phases, agents, gates

Agents run on devbox from the orchestrator session.
Each agent owns one directory, reads the upstream files named in its brief, and reports the commands it ran with real output.
After each agent finishes, the orchestrator reruns its oracle before anything is built on top.
A reviewer agent reads the port against upstream for the three hard modules (terminal, transport sender, overlay) and lists every semantic deviation.

### Phase 0: setup (done or one agent, under an hour)

- Devbox has apt mosh, build tools, rustup, upstream built at `~/src/mosh`. Done.
- Create the workspace, `CLAUDE.md`, `.gitignore`, release profile, four empty crates with their `Cargo.toml` and the dependency list from section 2.
- Verify `cargo build` of the empty workspace and `x86_64-pc-windows-gnu` target installation.

### Phase 1: four agents in parallel

- A. `crates/network`, medium effort. First builds `ref-crypto`. Gate: RFC 7253 vectors, random differential encrypt/decrypt both ways against `ref-crypto`, fragment and instruction round trips, two Rust endpoints syncing a toy state over `udp-impair` with 30% loss and an address change.
- B. `crates/terminal`, medium effort. First builds `ref-term` and `vt-check`. Gate: cell-exact on every upstream `emulation-*.test` input and every corpus file, byte-exact `new_frame` on all corpus state pairs, one million differential fuzz cases with zero mismatches.
- C. `crates/platform` and the launcher in `crates/mosh/src/launcher`, medium effort. Gate: raw mode on and off on a real pty, resize detected, the `--fake-proxy` address discovery, `MOSH CONNECT` parsing against real `mosh-server new` output, Windows crate compiles for the gnu target.
- H. `tools/`, medium effort. Gate: `udp-impair` demonstrably drops, delays, reorders, and rebinds; corpus recorded; `make check` in `upstream/` runs green with upstream's own binaries so the harness is known good.

### Phase 2: state sync, server, client

- B continues into `crates/mosh/src/statesync` (it knows the terminal API). Gate: `Complete` diff and apply round trips are cell-exact against `ref-term`.
- D. server, medium effort. Gate: C++ client connects to the Rust server and the interop matrix column passes.
- E. client without prediction, then the prediction overlay, medium effort. Gate: Rust client against C++ server passes the matrix column; prediction e2e shows the predicted character within 50 ms at 300 ms RTT and corrects on mismatch.
- Then the full matrix and upstream `make check` with our binaries. Fresh small agents per bug cluster.

### Phase 3: Windows

- Cross-compile, copy to laptop, run `mosh.exe devbox` in Windows Terminal. The lid-close test is manual.

### Phase 4: scrollback

- Server side, then client side, by two agents in sequence, medium effort, following section 6 exactly. Gate: oracle 6, plus the full interop matrix still green (old peers unaffected).

### Phase 5: performance and release

- `tools/bench` against C++ mosh, numbers into README.
- Public GitHub repo, GPLv3 with upstream COPYING and attribution, README with the compatibility matrix and measured numbers.
- GitHub Actions: linux x86_64 and arm64 (musl, static), macOS arm64, Windows x86_64 (MSVC). Tag v0.1.0.

## 11. Process rules for agents

- Read the upstream file before porting it. Keep names. Keep constants. Keep the order of operations.
- Never edit `upstream/`, `ref/` (except the agent assigned to it), or another agent's crate.
- Run the oracle for your module before reporting. Paste the command and its output.
- If upstream behavior is unclear, test upstream (`ref-*` or the real binaries) and match it. Do not guess.
- Any proposed deviation goes into the report as a question. It is not implemented until section 9 lists it.
- Commits: plain messages, no attribution lines.

## 12. Deferred

X forwarding, port forwarding, SOCKS (mosh never had them), IPv6 beyond what the interop matrix exercises, `--bind-server=IP`, Windows server.
