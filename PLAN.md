# mosh-rs: a Rust reimplementation of mosh

Version 2 of the plan, 2026-10-13.
Working name `mosh-rs` (rename before publishing).
License GPLv3, because the code is ported from upstream mosh (GPLv3, Keith Winstein et al.).
Port source: upstream git master at commit decd9b7 (2026-03-22, 39 commits after the `mosh-1.4.0` tag), which is what `~/src/mosh` on devbox contains. Interop and `make check` compatibility are proven against the mosh 1.4.0 release binaries from apt.
Goal: one static Rust binary per platform that talks to every existing mosh-server, runs natively on Windows, and adds scrollback.

All work happens on devbox (`~/mosh-rs`), inside a Claude Code session running in tmux.
Upstream source and a built upstream tree live at `~/src/mosh`, symlinked as `~/mosh-rs/upstream`.
Real mosh 1.4.0 from apt is installed on devbox as `mosh`, `mosh-client`, `mosh-server`.

## 0. Decisions

- Port upstream file by file, preserving control flow and every constant. Do not "improve" semantics. Every deliberate deviation is listed in section 9 and nowhere else.
- Correctness is proven by differential testing against upstream's own C++ code, by interop with real mosh in both directions, and by end-to-end tests. Not by unit tests.
- Protocol version stays 2. New features are additive protobuf fields that old peers ignore.
- No async runtime. One poll loop with a computed timeout, exactly like upstream's select loop.
- Four crates. No trait unless there are at least two real implementations.

## 1. What mosh is (what we are rebuilding)

A mosh session has four layers, bottom to top.

1. Crypto (`upstream/src/crypto`).
   Every UDP packet is AES-128 in OCB3 mode (RFC 7253) with a 16-byte tag.
   The 128-bit key is generated by the server, printed once over ssh as 22 base64 characters, and never sent again.
   The nonce is 12 bytes: 4 zero bytes then a big-endian u64 whose top bit is the direction (1 = to client) and whose low 63 bits are the packet sequence number.
   The wire packet is the 8 nonce bytes followed by the OCB ciphertext.
   Inside the plaintext: a 16-bit timestamp, a 16-bit timestamp echo (for round-trip timing), then the payload.
2. Transport, called SSP (`upstream/src/network`).
   Neither side streams bytes.
   Each side keeps numbered snapshots of a state object and sends a `TransportBuffers::Instruction`: old_num, new_num, ack_num, throwaway_num, and `diff`, the bytes that turn state old_num into state new_num.
   Diffs are zlib-compressed and split into fragments (id, fragment number, final flag) that fit in one UDP packet.
   The sender picks send intervals from measured round-trip time, retransmits when unacked, and the server adopts a new client address whenever a valid packet arrives from one.
   That last rule is roaming.
3. State objects (`upstream/src/statesync`).
   Client-to-server state is `UserStream`: an ordered list of keystroke and resize events (`userinput.proto`).
   Server-to-client state is `CompleteTerminal`: a full terminal framebuffer plus an echo-ack counter (`hostinput.proto`).
   The server-to-client diff is not raw program output.
   It is an ANSI escape string computed by `Display::new_frame` that redraws the client's mirror framebuffer from the old snapshot to the new one.
   The client feeds that string into its own copy of the emulator.
   So both ends run the same emulator, and the client's emulator must interpret that redraw subset exactly as upstream's does, or the mirror drifts and never recovers.
4. Frontend (`upstream/src/frontend`, `upstream/scripts/mosh.pl`).
   `mosh-server` parses `SSH_CONNECTION`, binds a UDP port in 60000-61000, prints `MOSH CONNECT <port> <key>`, forks, detaches from the ssh session, and runs the user's shell under a pseudoterminal.
   `mosh-client` puts the local terminal in raw mode, runs the poll loop, renders the mirror framebuffer to the real terminal, shows the status line, and runs the prediction overlay (local echo of typed characters, later confirmed or corrected by the server).
   `mosh` (Perl upstream) runs `ssh host -- mosh-server new ...`, reads the `MOSH CONNECT` line, and starts the client with the key in `MOSH_KEY`.

Upstream size: 16,964 lines of C++ and protobuf.
The terminal emulator (4,704 lines) and the prediction overlay (1,240 lines) are the hard parts.

## 2. Architecture

One Cargo workspace, four crates, plus tooling that is not shipped.

- `crates/terminal`: parser state machine, framebuffer, dispatcher, terminal functions, `Display` (render and `new_frame`).
  Pure Rust, no I/O, no platform code.
  Ported from `upstream/src/terminal`.
  Type and method names mirror upstream (`Complete`, `Framebuffer`, `DrawState`, `Cell`, `Row`, `Display`) so the frontend port can follow upstream line by line.
- `crates/network`: `crypto` (OCB3 session, key, nonce), `proto` (hand-written `prost` structs, no `.proto` compilation, no build script), `transport` (fragments, compression, sender, receiver, connection, timing, roaming).
  Transport is generic over a `State` trait with exactly the methods upstream's template requires: `diff_from`, `init_diff`, `apply_string`, `subtract`, `reset_input`, `compare` (the sender's verbose round-trip check, which upstream's `make check` greps for), and equality, plus `subtract_self` for upstream's `subtract( this )` call on the front state, which Rust borrows cannot express as aliasing (default: subtract a copy; `UserStream` overrides with clear, `Complete` with nothing).
  Sockets via `mosh-platform` (`mosh_platform::socket`); the crate itself has no `unsafe` and no `#[cfg]` platform code (`#![forbid(unsafe_code)]`).
  Ported from `upstream/src/crypto` and `upstream/src/network`.
- `crates/platform`: the only crate with `#[cfg(unix)]` and `#[cfg(windows)]` code, apart from the `#[cfg(unix)]` on `crates/mosh/src/server` and the `mosh-server` binary (the server is Unix-only).
  Local terminal: raw mode on and off, size query, resize detection, blocking byte reads on a thread, byte writes.
  Pseudoterminal: forkpty, window size, child wait (unix only).
  Process: spawn `ssh` and read its output (both platforms).
  UDP sockets for `crates/network` (`socket`: creation with upstream's options, numeric `getaddrinfo`, bind, `recvmsg` with the ECN mark) and core-dump control (`coredump`, unix only).
- `crates/mosh`: `statesync` (`UserStream`, `Complete`), the client (`stmclient`, `terminaloverlay`), the server, and the launcher.
  Produces three executables with upstream's names and flags: `mosh`, `mosh-client`, `mosh-server`.
  Upstream's test harness and existing user scripts work unchanged.
- `ref/`: tiny C++ programs linked against the upstream build, used as oracles. Not shipped.
- `tools/`: `udp-impair` (a UDP proxy with loss, delay, reordering, and client-address change), corpus recorder, perf bench. Not shipped.
- `tests/`: the end-to-end and conformance tests described in section 3, run with `cargo test --release` plus shell drivers.

Dependencies: `aes` (with its `zeroize` feature), `ocb3`, `rand`, `prost`, `flate2` (with the `zlib-rs` backend), `nix` (unix only), `libc`, `windows-sys` (Windows only), and `zeroize` (wipes the session key copy without `unsafe`, review F23).
`unicode-width` was replaced by a width table generated from glibc `wcwidth` (INTERVENTIONS.md, Phase 0) and is no longer declared.
`lexopt` is not used and no longer declared: the launcher ports mosh.pl's Getopt::Long parsing by hand (section 8), and `mosh-client` and `mosh-server` port upstream's `getopt`.
Nothing else without a reason written in the PR.

## 3. Correctness strategy (the oracles)

Each oracle is a program we can run, not an opinion.

1. Reference harnesses in `ref/`, built against upstream object files on devbox.
   - `ref-term dump W H`: reads bytes on stdin, feeds them to upstream `Terminal::Complete` at that size, dumps the framebuffer in a fixed text format (every cell: text, width, attributes, fg, bg; cursor; cursor visibility; title; mode flags).
   - `ref-term frame W H OLDFILE NEWFILE [initialized]`: feeds two byte streams, dumps upstream `Display(false).new_frame(initialized, old, new)` as bytes (`initialized` defaults to 1).
   - More modes for speed and later phases: `batch`, `steps` (byte and resize records, for the statesync round trip), `frame-batch`, `frame-resize-batch`, and `caps` (`ref/ref-term/README.md`).
   - `ref-crypto enc KEY DIR SEQ TS TSR` and `ref-crypto dec KEY`: key, direction, sequence number, timestamps and payload in, wire packet out, and the reverse; `ref-crypto vectors` prints the RFC 7253 vectors.
   Our Rust binaries `vt-check` and `crypto-check` take the same modes and print the identical formats; `tests/tests/terminal_conformance.rs` and `tests/tests/crypto_conformance.rs` run them.
   Conformance means `diff` is empty.
2. Differential fuzzing of the emulator.
   `vt-fuzz --cases N --jobs J --seed S [--size WxH] [--frames]` (`tests/src/bin/vt-fuzz.rs`) generates inputs biased toward escape sequences (CSI with random params, SGR, OSC, DEC private modes, UTF-8 including wide and combining characters, invalid bytes); with `--frames` it checks `new_frame` on random screen pairs, half of them across a resize.
   Each is run through `ref-term` and `vt-check`; the first mismatch is minimized and fixed.
   It is run by hand at gates (STATUS.md has each run), not by `tests/run-all.sh`.
   `new_frame` must be byte-exact against the reference on every pair of corpus states (`terminal_conformance`).
3. Corpus of real sessions, recorded on devbox with a pty recorder (`tools/src/bin/pty-record`, scripts in `tools/corpus/`): bash with colors, vim editing a file, less on a man page, htop, tmux inside the session, the Claude Code TUI, `seq 1 100000`, a 256-color and truecolor test, a wide-character and emoji test, and a resize.
   Every corpus file (`tests/corpus/sessions/`, plus the 17 inputs from upstream's emulation tests in `tests/corpus/emulation/`) is a conformance input for oracle 1.
4. Interop matrix over loopback through `udp-impair` (`tests/interop.sh`; the C++ side is apt mosh 1.4.0).
   {Rust client, C++ client} × {Rust server, C++ server} × {clean, 5% loss, 30% loss with 200 ms delay and reordering, 2-minute blackout, client address change mid-session} (profiles `clean`, `loss5`, `loss30`, `blackout`, `rebind`) × six scenarios (seq, colors, vim, wide, resize, typing).
   Each cell runs a scripted session inside tmux and compares the final `tmux capture-pane` to a direct (no mosh) run of the same script.
   Also asserts: typed keys echo after the blackout, and after the change the proxy forwards the server's packets to the client's new port.
   With no arguments it runs only the C++ pair with a 10 s blackout; `INTEROP_FULL=1` gives the 2-minute blackout.
   Loss starts once the session is up; `tests/interop-setup-loss.sh --run` covers setup with 30% loss from the first packet.
5. Upstream's own test suite (`tests/upstream-check.sh --client cxx|rust --server cxx|rust`).
   It copies the upstream tree to `target/upstream-check/mosh`, puts our `mosh-client` and `mosh-server` over the binaries in its `src/frontend/`, and runs `make check` there; `upstream/` is never written.
   Every upstream e2e test must pass with our binaries.
6. Scrollback oracle.
   tmux is the host terminal with `history-limit 200000`.
   Run `seq 1 50000` over mosh-rs, then `tmux capture-pane -S -200000` and compare scrollback plus screen to `seq 1 50000` exactly: no gaps, no duplicates, no blank lines.
   Repeat with 30% loss, with a vim excursion in the middle (vim output must not appear in scrollback), and with a resize in the middle.
   `tests/scrollback.sh` runs this as ten variants: clean, loss30, vim, clear, altscreen, resize, shrink, grow, oldserver and dropped (the vim, clear and resize variants use `seq 1 3000` and `seq 3001 6000` around the event).
7. Performance bench, compared with C++ mosh in the same harness (section 5): `tools/src/bin/bench` (`target/release/bench`), against apt mosh 1.4.0.
8. Human end-to-end.
   `mosh devbox` from WSL and from Windows Terminal over Tailscale, sleep the laptop, wake it, the session is live and scrollback works.

## 4. Testing rules

- No unit tests of individual functions. No mocks. No test-only traits or abstractions in shipped code.
- Every test exercises a feature a user would notice: screen correctness, survival under loss and roaming, scrollback integrity, prediction behavior under latency, exit codes, resource usage.
- Tests live in `tests/` as cargo integration tests or shell drivers, and run with one command: `tests/run-all.sh`.
- A test that cannot fail for a real reason is deleted.
- The agent that writes a module also makes it pass the relevant oracle before reporting. The report contains the commands and their real output.

## 5. Performance targets

Measured by `tools/bench` against C++ mosh 1.4.0 on devbox, and published in the README as measured numbers.

- Idle CPU of client and server over 60 seconds: 0.0% (no polling faster than the computed send interval).
- Resident memory, client and server, after a 1-hour session: no more than C++ mosh.
- Static binary size: under 4 MB.
- Startup: the client's own startup (exec to its first terminal write) under 20 ms, and the first frame on loopback no slower than C++ mosh. (The original target, first frame under 20 ms, cannot be met with upstream's timing: the round-trip estimate starts at 1000 ms (`network.cc` `SRTT( 1000 )`), so the first send interval is the 250 ms maximum, and both implementations show the first frame after about 252-257 ms.)
- Keystroke to screen with prediction: one render, no visible delay at 300 ms simulated RTT.
- `seq 1 100000` through mosh on loopback: no slower than C++ mosh.
- Release profile: `opt-level = 3`, `lto = "fat"`, `codegen-units = 1`, `panic = "unwind"` (the client restores the terminal from a panic hook).
- Linux releases are static musl binaries.

## 6. Scrollback design

Why upstream has none: the client enters the alternate screen (`Display::open` sends smcup), so the host terminal never scrolls and never accumulates history.
The server's framebuffer also discards rows that scroll off, so lines that pass between two frames are gone.
Upstream's `new_frame` already detects full-screen scrolls and emits newlines at the bottom row (`terminaldisplay.cc` lines 168-243), which is why a client patched to skip smcup gets partial scrollback with gaps and with the status line leaking into history.

Design, all gated on negotiation so old peers see byte-identical behavior:

1. Negotiation.
   New `ClientBuffers::Instruction` field 4, `ClientCapabilities { optional bool scrollback = 1; }`.
   The client puts it as the first event in its `UserStream`.
   Upstream `UserStream::apply_string` ignores unknown extensions (`user.cc` if/else-if chain), so an old server sees nothing.
   A new server that applies it turns scrollback mode on for that session.
   Encoded alone it is the `UserMessage` bytes `0a 04 22 02 08 01`; upstream's `UserStream::apply_string` was fed those bytes plus a keystroke and a resize and returned only the keystroke and the resize.
   Like any non-empty user diff, a diff holding only the capability registers an input frame on the server (one echo ack).
2. Server capture.
   The `Framebuffer::scroll` path records each row that leaves the top when the scroll region is the full screen and the remote program has not enabled the alternate screen (DEC mode 1049, 1047 or 47, tracked as a new flag in `DrawState`; upstream ignores those modes entirely).
   Rows created or last written while that flag is on carry a mark (`Row::alternate`, not part of row equality) and are never captured.
   In scrollback mode (capture on) the alternate screen is a real second screen, as in tmux (`Framebuffer::enter_alternate_screen`, `leave_alternate_screen`): setting DEC 47, 1047 or 1049 while the flag is off puts the main screen's rows aside (and the cursor, for 1049) and the program draws on a blank screen; resetting any of them brings the rows (and that cursor) back, so after vim the shell continues below the pre-vim screen, whose rows scroll into history later, in the order a host terminal over ssh shows.
   The saved rows follow resizes the way the shown screen does (cut or added at the bottom); a full reset (RIS) drops them.
   Without scrollback mode only the flag is recorded and upstream's single screen is kept, so old peers see upstream's bytes.
   Rows removed from the bottom by a height shrink were never scrolled off and are not history; they are lost exactly as upstream's framebuffer loses them.
   One more case makes rows history although they do not scroll (`Framebuffer::capture_screen`), because a host terminal over ssh would keep them: erasing the whole display with a full-screen scrolling region and the flag off (ED 2, or ED 0 from the home position) captures the rows from the top through the last non-blank one before the erase, as tmux 3.4 does (`scroll-on-clear`).
   (Before the real alternate screen, entering it captured the same rows; with the main screen saved and restored that is no longer needed, and would duplicate them.)
   `clear` on devbox sends `CSI H CSI 2J CSI 3J` for TERM=xterm-256color (what mosh-server sets), `CSI H CSI J CSI 3J` for tmux-256color and `CSI H CSI J` for screen.
   ED 3 (erase saved lines) stays ignored, as upstream: the host terminal's history belongs to the host, and mosh never erases it (tmux over ssh does: after `seq 1 30; clear` its history is empty, measured).
   Capture interface: the terminal crate knows nothing of mosh.
   `Framebuffer::set_scroll_capture(true)` makes `scroll` append the leaving rows (shared `Rc<Row>`, no copy) to a list that `Framebuffer::take_scrolled_rows` empties; `Complete::act` empties it after every call, so the list is always empty when a state is copied.
   Diffs applied with `apply_string` discard captured rows (a copy of a server state applying a diff, as the sender's round-trip check does, must not add history).
   Each captured row is rendered to an ANSI string with the same row renderer `new_frame` uses (`Display::render_scrolled_row`): `put_row` on an uninitialized one-row frame, assuming neither ECH nor back-color erase.
   A rendered row longer than `MAX_SCROLLED_LINE` = 256 KiB is kept as a dropped line instead (the client shows the drop notice in its place). Per cell the renderer writes at most a 50-byte SGR, a grapheme of up to 36 bytes and an OSC 8 link of up to 16 KiB (the parser's OSC limit), so only a row with a long new link in nearly every cell gets there (1000 columns with a 200-byte link per cell and truecolor stay below it).
   The line is written at row 1 column 1 with default renditions and no hyperlink, ends with default renditions and no hyperlink, holds no line feed and no cursor visibility change, and its only cursor movement is `CSI 1 ; <col> H` before the last cell of a row that wrapped.
   Blank runs are spaces except default-colored blanks at the end of the row, which are `CSI K`.
   A wrapped row does not carry its soft-wrap flag.
   Rendered lines go into the backlog (`ScrolledRing`), shared by `Rc` among all copies of the server's `Complete`, so copying `Complete` for the sender's state history stays cheap.
   The backlog holds only undelivered lines: every line at or below the count the client has acknowledged is freed.
   It is a backlog, not a history.
   It is capped in bytes of rendered lines: `mosh-server --scrollback N` in MiB, default 32 (`seq 1 50000` renders to 388,710 bytes, about 380 KiB, so it fits about 85 times over); 0 turns capture off.
   A `K` suffix gives KiB instead (`--scrollback 16K`), which the dropped-lines oracle uses.
   When the cap would overflow, the oldest lines not yet published are replaced by a count of dropped lines (a sixteenth of the cap more than needed, so a steady flood does not search on every line); published lines are kept, because they may have to be sent again.
   The server never blocks the remote program and never stops reading the pty: the framebuffer stays current and history trickles behind it.
   When the program's output ends while lines are still undelivered, the server keeps the session up until every line is acknowledged, or until no acknowledgement has advanced for 60 seconds (the client is gone), then shuts down as upstream does.
3. Wire.
   New `HostBuffers::Instruction` field 9, `ScrolledLines { optional uint64 first_index = 1; repeated bytes line = 2; optional uint64 dropped = 3; }`.
   Lines are numbered from 1 in the order they left the screen.
   `Complete` carries only `scrolled_total: u64`, the number of lines PUBLISHED, not captured.
   The server loop publishes (`Complete::publish_scrollback`) after host output and after every received packet: `scrolled_total` advances while the rendered bytes of lines published beyond `acked.scrolled_total` stay within the window W, where `acked` is the newest state the client acknowledged (front of the sender's sent states, read with the read-only accessor `Transport::get_sent_state_acked_state` that mosh-rs adds to the transport).
   At least one line is published when none is outstanding, even if it alone exceeds W, so a huge line cannot stall the stream; a dropped run is published whole and costs no bytes.
   Publishing changes the state, so the transport sends it; an arriving ack frees delivered lines and re-runs the publish check.
   W is 4 × 1214 = 4856 bytes: the payload of four fragments at upstream's IPv4 MTU (1280 - 28 IP and UDP - 12 nonce and timestamps - 16 OCB tag - 10 fragment header = 1214).
   With two bytes of protobuf framing per line, incompressible lines need at most six fragments plus one for the frame; `seq` lines compress about 4:1, and a live `seq 1 50000` never needed more than two fragments per instruction.
   `Complete::diff_from(existing)` sends the published lines numbered `(existing.scrolled_total, self.scrolled_total]`, one `ScrolledLines` instruction per run of held lines: `first_index` is the number of `line[0]` (one past the last number covered when the range ends in a gap and the instruction has no line), and `dropped` (absent when 0) counts the lines missing just before it.
   New `HostBuffers::Instruction` field 10, `ScreenMode { optional bool alternate_screen = 1; }`: sent in scrollback mode only, when the flag differs between the two states (`init_diff` sends it when the program is on the alternate screen); the client stores it in its framebuffer's `DrawState` flag. `Complete` equality includes the flag in scrollback mode only.
   Instruction order in a `HostMessage`: echo ack, scrolled lines, screen mode, resize, host bytes.
   A client prints the lines first, then applies the frame.
   `Complete` equality includes `scrolled_total` (0 on both sides unless the client asked for scrollback), otherwise publishing without a screen change would never be sent.
   Announcement: `Complete` also carries `scrollback_on`, set on the server when the capability turns capture on and on the client when any `ScrolledLines` arrives, and part of equality.
   A diff from a state without it to a state with it always holds a `ScrolledLines`; when no line is due, that is one instruction with `first_index = scrolled_total + 1`, no lines and no `dropped`.
   So the first frame a scrollback server sends says so, even before any line exists, and a client can tell an old server (no announcement) from a quiet one; `init_diff` (from a fresh state) carries it too.
   Without the capability the flag stays off and every diff is byte-identical to upstream's.
   `init_diff` sends only the count (as dropped lines), because the backlog no longer holds delivered lines; the sender's verbose check compares the init diffs of two states.
   Client side: `Complete::enable_scrollback_receive` returns a queue shared by every copy of the client's state; `apply_string` adds each line with its number, skips numbers it already has (a diff from an older state, sent again after loss, repeats lines) and counts a jump forward as lost.
   Each window needs about one round trip plus the client's 100 ms delayed ack: the history of `seq 1 50000` (about 380 KiB rendered) is complete after 9 s on loopback and 17 s at 100 ms round trip, while the final screen arrives as fast as without scrollback (0.25 s and 0.35 s).
4. Client rendering.
   Opt-in: `mosh --scrollback` starts the client with `MOSH_SCROLLBACK=1` (section 8); the client reads that variable, so `mosh-client` alone can be tested the same way.
   Without it the client is upstream's, byte for byte, and sends no capability.
   With it the client sends the capability as the first event and starts exactly as upstream, in the alternate screen, so the "Connecting..." and "Nothing received" messages never touch the host's main screen.
   It decides when the first frame from the server has been applied (`get_remote_state_num() != 0`): if the frame carried the announcement (6.3), it writes `close()` (which ends with rmcup: back to the main screen, cursor back where it was before mosh started), switches its `Display` to host-history mode (no smcup or rmcup from then on), and writes one CR LF per screen row, so the host's rows down to the cursor (the shell prompt that started mosh, and what was above it) scroll into the host's history before the first full repaint.
   Otherwise it stays in the alternate screen as upstream and shows "Server does not support scrollback; using the alternate screen." in the notification bar for 5 s (6.5).
   In host-history mode `new_frame` never moves a row into the host's history: the scroll shortcut is off, and a full repaint erases with `CSI H CSI K CSI 2;1H CSI J CSI H` instead of `CSI H CSI 2J`, because tmux 3.4 (option `scroll-on-clear`, on by default) moves the whole screen into its history on `CSI H CSI 2J` and on `CSI H CSI J`, but not on `CSI 2;1H CSI J` (measured).
   Its other writes cannot scroll the host either: the last cell of the last row leaves the cursor pending-wrap, and line feeds for cursor moves are only used above the last row.
   A frame whose size differs from the host window's (the host was resized and the server has not applied it yet) would wrap on the host and scroll it, so it is not drawn; history lines still are, and the next frame drawn is a full repaint (the host may have reflowed its screen meanwhile).
   Before each render, for each received line: `CSI H`, the line, `CSI 9999;1H` (the last row by clamping, so a resize the client has not processed yet cannot leave the line feed above the last row), line feed.
   The host terminal moves row 1 (which is now the line) into its history and shifts the screen up one row.
   The lines are never written as received: each is fed to a one-row emulator as wide as the host window, and every row that leaves it (a line wider than the window wraps) and its last row are drawn with `Display::render_scrolled_row`, so a line is always exactly one host row per emulator row and nothing the server sends reaches the host unparsed.
   The rows one line may make are bounded: the server's renderer never writes a line feed, so a real line only wraps, into at most ceil(frame width / host width) + 1 rows; the client stops feeding a line at that many rows (at least 4, for lines from before a resize to a narrower frame, at most 1024) and writes the dim line `[mosh: the rest of a history line was dropped (too many rows)]` after them. Before this bound (review G1) one line of 1,000,000 line feeds, about 1 KB on the wire, made the client hold one row per byte (4.1 GB); `tests/tests/scrollback_hostile.rs` drives the real client with crafted lines from `hostile-scrollback-server`.
   Where lines are missing (numbers jump, or the server reports a dropped run with no line after it), one dim (SGR 2) line `[mosh: N lines of history were dropped]` is injected at that place; it is written directly, because mosh's emulator drops SGR 2.
   Before the first line the client hides the cursor and resets renditions and the hyperlink (the lines assume both are default); after injecting S rows, `Framebuffer::host_scrolled(S)` shifts the client's last-frame copy up by S rows with blank rows appended and records the host's cursor (hidden, last row, column 1, default renditions), then `new_frame` runs as usual.
   For a one-line scroll this degenerates to one newline plus one row repaint, same cost as today.
   The notification bar and prediction underlines are drawn into row 1 and other rows of the frame, never injected: the only row that enters the host's history is row 1, and it always holds an injected line at that moment.
   The whole render is wrapped in synchronized output (`\e[?2026h` ... `\e[?2026l`), which terminals that lack it ignore.
   The host follows the program's screen (item 6): when the server's flag turns on, the client injects the lines received so far (they left the main screen before the switch), writes `CSI ?1049h` and repaints; when it turns off, it writes `CSI ?1049l` (the host brings back its main screen and cursor), injects the lines received meanwhile (they left after the switch back) and repaints; while the host shows its alternate screen no line is injected, they wait in the queue.
   Exit: the final screen stays (no rmcup), `close()` restores the terminal modes, and the cursor goes to the start of the first row below the screen's text (or the cursor's row, if lower), where `[mosh is exiting.]` is printed; if the host is in its alternate screen, the client leaves it instead and the message goes where the host's main-screen cursor was.
   Suspend (escape key, Ctrl-Z): the host leaves its alternate screen if it is in it, the screen is erased without entering history (it is mosh's screen, not history; the server sends its rows later when they scroll off) and the local shell gets an empty screen; on resume what the local shell printed is scrolled into history the same way as at startup, then the screen is repainted (in the alternate screen again if the program is still there).
   Known limits, measured with tmux as the host (`tests/scrollback.sh`):
   - Height shrink by k with the cursor on the last row: tmux moves its top k rows into its own history, and they arrive again when they scroll off on the server, so they appear twice; the server's emulator cuts the bottom k rows as upstream's does, so they never reach history (2978-2983 twice and 2995-3000 missing, for k = 6 after `seq 1 3000`).
   - Height growth by k: tmux pulls its last k history lines back onto the screen and the repaint overwrites them, so they are gone from history (2972-2977 for k = 6 after `seq 1 3000`).
   Both come from the host terminal and the server's emulator resizing differently (the host keeps the bottom, upstream's framebuffer keeps the top); the client cannot know how a given host resizes.
   - A line wider than the host window wraps into several history rows, but a row that had wrapped on the server carries `CSI 1;<col>H` with the server's column, which clamps at the host's last column, so its last cell overwrites the one before it.
   - With `--no-init` there is no alternate screen to start in, so the "Connecting..." bar and the first frame land on the main screen, as upstream.
   Width changes, vim, `clear` and everything else in the oracle are exact.
5. Compatibility.
   Old client, new server: no capability arrives, scrollback mode stays off, behavior identical to upstream.
   New client, old server: the first frame carries no announcement, so the client stays in the alternate screen exactly as upstream (no history accumulates, nothing reaches the host's main screen) and shows the one-line notice in the notification bar for 5 s.
   The same happens with a mosh-rs server started with `--scrollback 0`.
6. Alternate screen forwarded (done after oracle 6 passed).
   In scrollback mode the server keeps a real alternate screen (item 2) and sends its flag (item 3); the client writes `CSI ?1049h` and `CSI ?1049l` on its transitions, each with a full repaint inside synchronized output (item 4).
   So the mouse wheel inside vim or less does what the host does in its alternate screen, and when the program exits the host shows the pre-vim screen and the prompt, as over ssh (`tests/scrollback.sh altscreen` compares it with a plain tmux pane).
   History stays exact: the main screen's rows are neither captured on entry nor lost; they scroll off later, once.

## 7. Windows client

- Console setup: `SetConsoleMode` with `ENABLE_VIRTUAL_TERMINAL_PROCESSING` and `DISABLE_NEWLINE_AUTO_RETURN` on stdout and `ENABLE_VIRTUAL_TERMINAL_INPUT` on stdin, processed, line and echo input off, `SetConsoleCP`/`SetConsoleOutputCP` to UTF-8; the saved modes and code pages are restored on exit.
  After that, keys arrive as the same escape-sequence bytes a unix tty produces, and output is plain VT bytes.
  No key-event decoding and re-encoding layer.
- Input: the select loop polls sockets only, so a thread reads the console with `ReadConsoleW` (UTF-16, converted to UTF-8) and forwards the bytes over a loopback TCP connection whose receiving socket the loop watches.
- Resize: while the client watches SIGWINCH, `Select::select` caps its wait at 50 ms and compares the `GetConsoleScreenBufferInfo` window size after every call, raising SIGWINCH when it changed.
- Ctrl+C arrives as byte 0x03 and goes to the server like any key.
  The escape key is Ctrl-^ as upstream, typed as Ctrl+6 in Windows Terminal.
- Ctrl+Break cannot be turned off by the console mode, and Windows' default handler ends the process without restoring the console.
  The client's `Select::add_signal(SIGINT)` installs a console control handler that turns Ctrl+Break (and a generated Ctrl+C event) into SIGINT, which the main loop handles as upstream handles SIGINT: a clean shutdown that restores the console on the way out.
  The handler only sets a pending flag that `select()` moves into the signal set after it polls (as unix keeps a blocked signal pending until `pselect`), and the wait is capped at 50 ms while it is installed, so the flag is noticed promptly.
  `mosh.exe`, which waits for `mosh-client.exe`, ignores the event so it does not give the console back before the client has finished.
  Close, logoff and shutdown events keep the default handling; the console goes away with the process.
- Console setup errors, including a failure to start the input thread, are returned from `raw_mode_on`, and the client prints them and exits 1 as it does for a failed `tcgetattr` (section 9 item 11).
- ssh: spawn `ssh.exe` from the Windows OpenSSH that ships with Windows 10 and later.
- Build: cross-compile on devbox for `x86_64-pc-windows-gnu` with the mingw package already available there, copy the exe to the laptop for testing. Releases use the MSVC target built on a Windows GitHub Actions runner.
- `mosh-server` is unix only, as upstream.
- TERM: Windows normally has none. If TERM is unset or empty when `mosh.exe` or `mosh-client.exe` starts, it sets `TERM=xterm-256color` for itself and its children (`mosh_platform::tty::default_term_if_unset`, section 9 item 12), which Windows Terminal and conhost with VT processing implement. On unix nothing changes.

## 8. Launcher

The launcher ports mosh.pl, including its address discovery: it runs ssh with `-S none -o ProxyCommand='<own exe>' '--family=<family>' --fake-proxy -- %h %p`.
In that mode the launcher resolves `%h` (the hostname after `~/.ssh/config`) with the system resolver (MagicDNS names like `devbox` resolve to the Tailscale address), orders or filters the addresses by `--family`, opens a TCP connection to the first one that accepts it on `%p`, prints `MOSH IP <address>` on stderr and relays the ssh session over that connection.
So mosh-server sees that address in `SSH_CONNECTION` and binds it, and the client is started with the same address; on hosts with both IPv4 and IPv6 addresses the two cannot disagree.
Host key checking is untouched because ssh still connects to the name the user typed.
An earlier design (`ssh -G`, then resolving the name separately) was dropped: on dual-stack hosts ssh and the client could pick different address families (INTERVENTIONS.md, 2026-10-13), and `-o HostName=<ip> -o HostKeyAlias=...` cannot reproduce ssh's known_hosts lookup for non-default ports (`[host]:port` with fallback to `host`).
Options are mosh.pl's complete set, parsed as its Getopt::Long configuration does: options and arguments may be mixed until `--`, `-x` and `--x` are the same, long names match case-insensitively and by any unique prefix (`--pred` is ambiguous between `predict` and `predict-overwrite`, `--loc` is `--local`), `!` options also take `--noNAME`/`--no-NAME`, there is no bundling (`-an` is the unknown option `an`), and a value is `--name=value` or the next argument whatever it looks like.
Getopt::Long's warnings, every `die` message (without Perl's `at SCRIPT line N.` suffix where mosh.pl's message has no newline, section 9 item 17) and the exit codes (Perl's `$!`: 10 after the ssh child is reaped, 29 inside the read loop, the resolver's errno after a failed lookup) are reproduced; `tests/tests/launcher.rs` compares 73 argument and environment cases with `/usr/bin/mosh`.
`--experimental-remote-ip=(local|remote|proxy)` is ported as in mosh.pl (default `proxy`, the mode described above).
In `proxy` mode the `-S none` means an open ssh ControlMaster socket is not used (upstream issue #24); `remote` and `local` run ssh without it and reuse the socket. mosh-rs adds a hint in that case (section 9 item 18).
`resolvename` follows mosh.pl: the host as a numeric address first, else its canonical name (AI_CANONNAME) resolved again, through `getaddrinfo` in `crates/platform/src/netdb.rs`.
The color count keeps `chomp` semantics: one trailing newline is removed, so a `mosh-client -c` output of `256\n\n` is passed on as `256\n`, as mosh.pl does.
The default client is `mosh-client` (`mosh-client.exe` on Windows) next to the launcher's own executable when that file exists, else `mosh-client` from PATH as mosh.pl (section 9 item 16), because the release archives ship the binaries side by side in a folder that is usually not on PATH.
`--scrollback` (mosh-rs only) and the restriction of `--bind-server` to `ssh` and `any` (section 9.3) are the only differences in the option set and usage text; `--scrollback` also makes `--s` ambiguous with four names instead of three.
`--scrollback` (listed in the usage text) starts the client with `MOSH_SCROLLBACK=1`, as mosh.pl passes `--predict` in `MOSH_PREDICTION_DISPLAY`; the client then asks the server for history (section 6.4).

## 9. Deviations from upstream (the only allowed ones)

1. Withdrawn (was: launcher uses `ssh -G` instead of `--fake-proxy`). The launcher ports `--fake-proxy` as mosh.pl does (section 8). The number is kept so references to items 2-10 stay valid.
   The Windows quoting of the ProxyCommand has no upstream counterpart and is described in sections 7 and 8; the sibling `mosh-client` lookup is item 16.
2. utmp/wtmp records are not written.
3. `--bind-server` supports `ssh` and `any` only.
4. Scrollback extension (section 6), alternate-screen flag in `DrawState`.
   This includes `mosh-server --scrollback MIB` (listed in its usage line, `K` suffix for KiB), and the read-only `Transport::get_sent_state_acked_state` the server uses to pace published lines.
   Server side, only in scrollback mode: the real alternate screen (6.2) and `ScreenMode` (6.3).
   Client side, only with `MOSH_SCROLLBACK=1` (`mosh --scrollback`): the capability, the deferred alternate-screen decision, `Display`'s host-history mode (`Display::set_host_history`), line injection with `Framebuffer::host_scrolled`, the notice line and the old-server notice, following the program's alternate screen (6.6), and the exit and suspend handling of section 6.4.
5. Synchronized output around client renders.
6. Runtime terminfo lookup is replaced by a table generated at build-authoring time from every entry in the devbox terminfo database (ncurses 6.4, plus the kitty-terminfo package), holding exactly the capabilities upstream reads (ech, bce, smcup, rmcup, and what it uses for title support). An exact TERM match gives the same answer upstream would get; an unknown TERM falls back to xterm where upstream would fail to start. The table also carries `colors`, so `mosh-client -c` answers from it; for an unknown TERM it prints xterm's count where upstream prints "unknown terminal type" and exits 1. Needed because Windows has no terminfo.
7. Timestamps start at 1,000,000,000 ms instead of milliseconds since boot, so upstream's `now - 0` comparisons behave as they do on a machine that has been up for a while.
8. Malformed input from a peer that holds the session key returns an error and drops the packet where upstream aborts the process with `fatal_assert` or `assert` (short fragment, conflicting duplicate fragment, fragment index past the final one, undecodable protobuf, `throwaway_num` above every received state, oversized ciphertext handed to `Session::decrypt`, and a state diff that `State::apply_string` cannot apply: a `UserMessage` or `HostMessage` that does not decode, a resize below 1x1 in either, host bytes that make the client emulator reply, an echo ack lower than the current one, and, from the mosh-rs scrollback extension, scrolled lines that go backwards, a history line longer than 256 KiB (`MAX_SCROLLED_LINE`, which a mosh-rs server never sends, section 6.2) or a line number above 2^63, so the client's numbering cannot overflow). `State::apply_string` returns `Result` for this.
9. Two places where upstream dereferences an erased iterator (undefined behavior) are made defined: `add_sent_state` moves `assumed_receiver_state` to the previous element when the assumed one is erased, and `Transport::recv` looks the reference state up again after `process_throwaway_until` and drops the instruction if it is gone.
10. Withdrawn (was: the `State` trait omits upstream's `compare`). `compare` is back in the trait and the sender runs upstream's verbose round-trip check, so upstream's `make check` catches a wrong server diff in our binaries too. The number is kept so references to item 11 stay valid.
11. Where upstream's client crashes or aborts with the terminal left raw, the client exits cleanly: if the window size cannot be read at startup it prints the error and exits 1 (upstream returns early from `STMClient::init` and then dereferences a missing network object, `stmclient.cc` lines 247-250), and a panic restores the terminal through the panic hook (section 5).
11a. Where upstream formats a notification with `swprintf( tmp, 128, ... )` (`terminaloverlay.cc` network errors and the bar text, `stmclient.cc` "Nothing received" and crypto messages) and the text does not fit, the client keeps exactly the first 127 characters (`swprintf128`, review G5).
     On glibc this is not a deviation: measured on devbox (2026-10-13), glibc returns -1 but leaves the first 127 characters and a terminator in the buffer, which upstream then shows.
     The item is kept so the review's reference stays valid.
12. On Windows only, `mosh` and `mosh-client` set `TERM=xterm-256color` for themselves when TERM is unset or empty at startup (section 7). Upstream's client prints "TERM environment variable not set." and exits 1 there, so the launcher stops with "Can't count colors" and a stock Windows Terminal could never connect. Unix keeps upstream's behavior.
13. Version strings name mosh-rs, not upstream: `mosh --version` prints `mosh-rs 0.1.0 [build 0.1.0]`, and `mosh-client` and `mosh-server` print `(mosh-rs 0.1.0) [build 0.1.0]` where upstream prints `(mosh 1.4.0) [build decd9b7]`, also in the server's banner (review G6; the binaries must not claim to be upstream).
14. The server session child flushes stdout before `execvp`.
    Upstream does not, so when `mosh-server new`'s stdout is a file or pipe (fully buffered), its motd and detached-session warning are lost at the exec; ours prints them.
    Through ssh's terminal, the normal case, both print them (STATUS.md, detached-session warning).

15. On Linux x86_64 and aarch64, `mosh-server` reads the utmp file (`/run/utmp`, else `/var/run/utmp`) with glibc's `struct utmpx` record layout instead of calling `getutxent()`, for the detached-session warning (mosh-server.cc line 1046), because musl's `getutxent` is a stub that never returns a record, so a static musl `mosh-server` would never warn. Reading the file the same way in the glibc and musl builds keeps them identical. A file whose size is not a whole number of records yields no records, as `getutxent` does for a file it cannot use. Other systems call `getutxent()`.

16. The launcher runs `mosh-client` (`mosh-client.exe` on Windows) from next to its own executable (`std::env::current_exe()`) when that file exists, and only otherwise `mosh-client` from PATH as mosh.pl line 64 does, on every platform (`mosh_platform::process::default_client_program`). The release archives ship `mosh`, `mosh-client` and `mosh-server` side by side in a folder that is usually not on PATH; without this, `./mosh` from the extracted folder fails with `Can't exec "mosh-client"` and `Can't count colors` (INTERVENTIONS.md, macOS verification item 4). `--client` still overrides it.

17. Launcher text that only makes sense for a Perl script is not copied: the usage text points bug reports at https://github.com/Arunjay4213/mosh-rs/issues instead of mosh-devel@mit.edu (issue #42; the Keith Winstein copyright lines stay), and the four `die` and `warn` messages that mosh.pl writes without a newline (`Unknown parameter`, `Died`, `could not find address for`, `Can't exec`) are printed without Perl's `at SCRIPT line N.` suffix. `tests/tests/launcher.rs` strips that suffix from mosh.pl's output before comparing.

18. In the default `--experimental-remote-ip=proxy` mode, the launcher first runs `<ssh> -O check <userhost>` (output discarded) and, when it exits 0 (an ssh ControlMaster socket is open for that host), prints one line to stderr before ssh runs: `mosh: ssh has a ControlMaster socket for HOST, but the default address discovery opens a new connection (ssh -S none); use --experimental-remote-ip=remote to reuse the socket.`
    Behaviour is otherwise unchanged (the session still uses `-S none`, as upstream), so the 73 launcher message cases still match mosh.pl, which never prints this. Nothing is printed when `-O check` fails for any reason (no ControlPath, no socket, an ssh wrapper without `-O`, Windows OpenSSH).

Anything else that differs from upstream is a bug.

## 11. Process rules for agents

- Read the upstream file before porting it. Keep names. Keep constants. Keep the order of operations.
- Never edit `upstream/`, `ref/` (except the agent assigned to it), or another agent's crate.
- Run the oracle for your module before reporting. Paste the command and its output.
- If upstream behavior is unclear, test upstream (`ref-*` or the real binaries) and match it. Do not guess.
- Any proposed deviation goes into the report as a question. It is not implemented until section 9 lists it.
- Commits: plain messages, no attribution lines.
